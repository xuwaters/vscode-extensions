# What has to be measured, and in what order

**Status**: gates closed and budgets measured 2026-08-23 — results in
[measurements.md](measurements.md). This page keeps the original method for
the record; per-item outcomes are marked inline.

This page exists because [proposal.md](../proposal.md) makes exactly one performance argument — that
template analysis is a per-keystroke workload under enough time pressure that lit-analyzer ships a
150 ms bail-out — and **does not** claim a number for what a Rust engine would do instead. No
benchmark has been run. Until one has, no number should be quoted, in this RFC or anywhere citing it.

Two of the spikes below are *gates*: if they fail, the design changes. The rest are budgets to
establish, not risks to retire.

---

## Gate 1 — Can the plugin be packaged at all?

**Task**: [P1-09](../tasks/phase-1-foundation.md) · **Blocks**: everything

> **Outcome (2026-08-23): PASSED, via fallback 3.** Fallback 1 is structurally
> impossible — vsce's collector globs with `ignore: 'node_modules/**'` before
> `.vscodeignore` is read. `scripts/inject-tsplugin.mjs` rewrites the VSIX
> after packaging; `scripts/verify-vsix.mjs` extracts the result and resolves
> the plugin exactly as tsserver's probe does, loads the factory against the
> real TypeScript, and runs the engine. The clean-VS Code TS-Server-log
> confirmation remains a manual desktop step. Details:
> [decisions/README.md](../decisions/README.md#open-questions--all-closed), question 1.

tsserver resolves plugins from `<probeLocation>/node_modules/<pluginName>`, and VS Code passes the
extension's install directory as a probe location. So the VSIX must contain
`node_modules/wx-fast-element-tsplugin/` with a `package.json` and a `main`.

This repo packages every extension with `vsce package --no-dependencies`, which is a statement that
no `node_modules` is needed at runtime. The two are in tension.

**What to try, in order:**

1. `.vscodeignore` negation — `!node_modules/wx-fast-element-tsplugin/**` after the shared template's
   rules. Note that `.vscodeignore` here is generated by `pnpm sync-vscodeignore` from a shared
   template, so an exception needs a per-extension mechanism, not a hand edit that the next sync
   erases.
2. Drop `--no-dependencies` for this one extension and let vsce walk a pruned dependency tree.
3. A post-`package` step that injects the directory into the `.vsix` zip.

**Pass**: a built VSIX, installed into a clean VS Code, whose plugin is loaded by tsserver — confirmed
from the TS Server log, not inferred from the absence of errors.
**Fail**: none of the three work → the extension ships the plugin some other way, or the whole
delivery model is re-decided in [0001](../decisions/0001-tsserver-plugin-not-lsp.md).

## Gate 2 — Does our parser match parse5?

**Task**: [P1-05](../tasks/phase-1-foundation.md) · **Blocks**: Phase 2

> **Outcome (2026-08-23): PASSED.** `test/parser-differential.test.ts`: 25
> fixture cases plus every corpus template match parse5's tree; the deliberate
> divergences (unclosed stays unclosed, self-close flagged, no synthesized
> `tbody`, placeholders first-class) are asserted as our behaviour rather than
> allowed silently. [0003](../decisions/0003-own-template-parser.md) stands;
> `swc_html_parser` was not needed. One caveat: lit-analyzer's own parser
> fixtures were not replayed — `temp/fast-analyzer` is not in this checkout.

[0003](../decisions/0003-own-template-parser.md) chooses to write a tolerant HTML parser rather than
bind an existing one, on the grounds that we need spans parse5 does not expose and tolerance
`html5ever` does not offer. That is a claim about a large, fiddly specification.

**Method**: a differential harness over

- the 26 templates in [corpus.md](corpus.md), substituted exactly as the virtual document does,
- lit-analyzer's own parser fixtures (`temp/fast-analyzer/packages/lit-analyzer/src/test/parser/`),
- a hand-written adversarial set: raw-text elements (`<style>`, `<textarea>`, `<title>`), foreign
  content (`<svg>`, `<math>`), implied end tags (`<li>`, `<p>`, `<tr>`), attribute values with `<`
  and `>`, placeholders in every legal position.

Compare tree shape and every span against parse5's `sourceCodeLocationInfo`. **Deliberate**
divergences — unclosed tags stay unclosed instead of being auto-closed, because `no-unclosed-tag`
depends on it — are enumerated in the harness as expected differences, not silently allowed.

**Pass**: no unexplained divergence on any input.
**Fail**: switch to `swc_html_parser`, which has spans and error recovery, and record the reversal as
a superseding ADR.

## Budget 1 — Cold and warm diagnostics

**Task**: [P5-04](../tasks/phase-5-polish.md)

> **Measured**: warm 0.73 ms, cold 383 ms including building the whole
> program from nothing (which tsserver never re-pays). No bail-out was
> implemented and none is needed. The fast-analyzer side-by-side is still
> open (`temp/` absent). [measurements.md](measurements.md).

What to measure, per file, with `logging: verbose` and the plugin's own timing wrapper:

| | Why |
| --- | --- |
| Cold `getSemanticDiagnostics` on the largest corpus file (pdf-ultra, 445 lines) | The number that has to fit inside a save |
| Warm, after a one-character edit | The number that has to fit inside a keystroke |
| The same two with the engine disabled (`fastElementUltra.disable: true`) | Isolates our cost from tsserver's |
| The same two on a synthetic template 10× the size | Whether cost is linear in template size |

The interesting comparison is against `temp/fast-analyzer` on the *same* inputs, with its FAST
component discovery patched to actually find the elements — otherwise it is doing less work and the
comparison is meaningless. That patch is part of the task.

**No target is set here on purpose.** A target invented before a measurement is a number people
quote. What the budget has to satisfy is stated as a behaviour instead:
[proposal.md §9](../proposal.md#9-success-criteria) — no wall-clock bail-out on a cold pass, and a
warm pass fast enough to run per keystroke without the analyzer needing one.

## Budget 2 — WASM instantiation and memory in tsserver

**Task**: [P5-04](../tasks/phase-5-polish.md)

> **Measured**: 588 KB raw / 213 KB gzipped; 1.7 ms fresh-process compile;
> no RSS growth over 1,000 edit cycles at 0.059 ms per cycle. Instance model
> resolved: one instance per process, one registry per project.
> [measurements.md](measurements.md).

The engine lives inside tsserver, a process the user did not choose to spend memory on. Measure:

- Artifact size, raw and gzipped.
- Time to compile the `WebAssembly.Module` once, and to instantiate per project.
- Resident heap after analysing the corpus, and after 1,000 edits — the engine caches parsed
  documents and a component registry, and neither should grow without bound.
- What happens with 5 open projects: one module, five instances, or one instance keyed by project?
  This is [open question 5](../decisions/README.md#open-questions).

## Budget 3 — Type-oracle round trip

**Task**: [P3-09](../tasks/phase-3-diagnostics.md)

> **Measured**: 32 facts / 13 documents (csv-ultra), 60 / 11 (pdf-ultra) —
> the batch is smaller than the binding count, one crossing per document each
> way, and answering it is inside the 0.73 ms warm pass.
> [measurements.md](measurements.md).

[0002](../decisions/0002-rust-engine-typescript-oracle.md) claims one boundary crossing per file is
enough, by batching binding facts. Measure the batch size on real files and the cost of answering
one, so that the claim is either confirmed or replaced with a real number. `pdf-ultra`'s template
carries roughly 80 bindings in 445 lines and `csv-ultra`'s roughly 55 in 371; a per-binding round
trip would be that many crossings per diagnostic pass, which is what the batching exists to avoid.
Only a fraction of those bindings reach a type rule at all, so the batch is smaller than the binding
count — by how much is part of what this measures.

## What is deliberately *not* being measured

- **Whether Rust is faster than TypeScript at this.** Interesting, and not decision-relevant: the
  fallback if the engine disappoints is a TypeScript engine behind the same protocol
  ([proposal.md §8](../proposal.md#8-alternatives-considered)), which is a substitution, not a
  rewrite. The measurement that matters is absolute — does it fit in a keystroke — not relative.
- **Parser throughput in MB/s.** Templates are kilobytes. Throughput is not the constraint;
  per-invocation overhead is.
